# Practical Work and Evidence Register

This register distinguishes a **studied activity or example** from a **verified laboratory result**. The uploaded materials include lecture exercises, syntax checkers, sample topology/configuration diagrams, worksheets, study questions and discussion screenshots, but no independently attributable, privacy-reviewed sequence of actual device CLI output and traffic tests. **No lab below is represented as successfully executed.** These are individually scoped lab evidence records, not fabricated reports.

## Lab A — Administrative Access and Router Hardening

**Objective:** restrict console/VTY access, use SSH instead of Telnet, apply login protections and verify permissions. **Topology in source:** router plus local console/remote administrative host (lecture conceptual diagram; exact lab wiring not verified). **Configuration studied:** `hostname`, `ip domain-name`, `crypto key generate rsa`, `ip ssh version 2`, `line vty`, `login local`, `transport input ssh`, `exec-timeout`, `login block-for`, `login quiet-mode access-class`, CLI views. **Why:** protect credentials in transit, constrain source access, mitigate guessing and restrict commands. **Expected:** valid SSH works; unauthorized source/credentials and Telnet are rejected; idle sessions expire; permitted commands succeed while privileged commands are denied. **Actual observed result:** not supplied. **Troubleshooting/verification still needed:** IOS image and SSH key state, `show ip ssh`, `show ssh`, `show login failures`, anonymized allowed/denied login transcripts and view tests.

## Lab B — Centralized AAA and Fallback

**Objective:** authenticate a network administrator through RADIUS/TACACS+ and test local fallback on server unreachability; separately verify authorization/accounting. **Topology in source:** router as network access device, AAA server and remote administrator. **Configuration studied:** `aaa new-model`, server definitions (private key omitted), `aaa authentication login` default/named lists, VTY method-list assignment and `aaa authorization`/`aaa accounting`. **Why:** centralize identity and privilege decisions without creating an uncontrolled administrative lockout. **Expected:** accepted/rejected users reflect server policy; fallback applies only on supported error/unreachable conditions; command authorization and accounting events can be audited. **Actual result:** not supplied. **Troubleshooting needed:** protocol ports, source interface, method-list binding, server reachability, redacted debug and backend accounting evidence.

## Lab C — Extended ACL Traffic Filtering

**Objective:** apply an extended ACL that denies one defined service from a source subnet while permitting other specified traffic. **Topology in source:** routers with distinct LAN endpoints and directional interface filtering in course questions; exact executed Packet Tracer file absent. **Configuration studied:** `ip access-list extended`, numbered ACEs, wildcard masks, `ip access-group ... in|out`. **Why:** enforce least-privilege Layer 3/4 filtering before traffic crosses a boundary. **Expected:** TCP/80 blocked for the specified source/destination while explicitly allowed traffic succeeds; ACL counters reflect test packets. **Actual result:** not supplied. **Troubleshooting needed:** source/destination inversion, subnet/wildcard errors, first-match order, interface direction, `show access-lists` and bidirectional test evidence.

## Lab D — Stateful and Zone-Based Firewall

**Objective:** restrict traffic between an inside and outside security zone, permit selected web egress and statefully allow return packets. **Topology in source:** inside/outside or private/Internet zones joined by a Cisco IOS router; course diagrams include a DMZ design. **Configuration studied:** `zone security`, `class-map type inspect`, `policy-map type inspect`, `zone-pair security`, `service-policy type inspect`, `zone-member security`. **Why:** map approved services to **directed** zone-pair actions. **Expected:** inside-initiated permitted flow and established return traffic succeed with `inspect`; unsolicited outside-initiated sessions fail; `pass` does not create return state. **Actual result:** not supplied. **Troubleshooting needed:** complete zone-to-interface mapping, direction, self-zone reachability, `show zone-pair security`, `show policy-map type inspect zone-pair sessions`, counters and packet-flow outputs.

## Lab E — SPAN and IDS Observation

**Objective:** mirror an authorized switch source port/VLAN to an IDS capture port and validate captured traffic visibility. **Topology in source:** switch carrying two endpoints with a dedicated monitor destination. **Configuration studied:** `monitor session ... source`, `monitor session ... destination` and `show monitor`. **Why:** an off-path IDS needs a representative traffic copy. **Expected:** source traffic visible on sensor while production forwarding continues independently; dropped mirror frames assessed under load. **Actual result:** not supplied. **Troubleshooting needed:** SPAN mode, correct source direction, monitor-port constraints, link status and redacted captures.

## Lab F — Cisco IOS IPS Signature Management

**Objective:** enable compatible IOS IPS, load a signed signature package, tune category activation and observe a controlled detection. **Topology in source:** IPS-capable router between authorised traffic generator and test target. **Configuration studied:** IPS directory/key/rule setup, signature package, `ip ips signature-category`, `retired true/false`, event/alert handling. **Why:** ensure only relevant signatures consume resources and map alarms to prevention actions. **Expected:** selected signatures loaded; permitted benign traffic unaffected; a controlled known-pattern test generates a traceable event and an action consistent with policy. **Actual result:** not supplied. **Troubleshooting needed:** software/package compatibility, installed signature status, interface direction, alert ID/action, dropped-packet observation and false-positive review.

## Lab G — Switch Port Security and CAM Protection

**Objective:** limit MAC learning on an access port and validate the chosen violation mode. **Topology in source:** access switch plus authorised endpoint(s), conceptual additional forged-MAC source. **Configuration studied:** `switchport port-security`, maximum count, static/sticky MAC, `protect|restrict|shutdown` and aging. **Why:** limit CAM-table abuse and unauthorized endpoint attachment. **Expected:** approved MAC remains connected; excess MAC is handled per configured violation mode; counter/log/port status agrees. **Actual result:** not supplied. **Troubleshooting needed:** voice VLAN/phone MAC requirements, sticky address persistence, err-disable/recovery and `show port-security` evidence. Any adversarial traffic requires explicit lab authorization.

## Lab H — DHCP Snooping and Dynamic ARP Inspection

**Objective:** block rogue DHCP offers and invalid ARP bindings on client access ports without interrupting valid clients. **Topology in source:** switch, approved DHCP service and client VLAN; separate ARP inspection reference drawing. **Configuration studied:** `ip dhcp snooping`, VLAN enablement, trusted server-facing uplink, access-port rate limit, `ip arp inspection vlan`, DAI trust. **Why:** protect address allocation and IP-to-MAC integrity at Layer 2. **Expected:** legitimate DHCP lease creates binding, forged offer/ARP is rejected, counters increase where appropriate and ordinary client connectivity works. **Actual result:** not supplied. **Troubleshooting needed:** `show ip dhcp snooping binding`, `show ip arp inspection statistics`, static-IP exemptions, uplink trust mistakes, rate limits and redacted DHCP/ARP traces.

## Lab I — Management Telemetry and Routing Integrity

**Objective:** establish NTP timing, inspect syslog/SNMPv3 access restrictions and validate routing-neighbour authentication where supported. **Topology in source:** network device(s), management/log/time service, routing peer. **Configuration studied:** `logging`, SNMPv3 security concepts, `ntp trusted-key`, `show ntp associations`, `show ntp status`, OSPF authentication mechanisms. **Expected:** synchronized clock, appropriate severity events, authorized SNMPv3 retrieval and authenticated routing adjacency with rejection on mismatched key. **Actual result:** not supplied. **Troubleshooting needed:** time source, MIB/privilege scope, key-ID/algorithm compatibility, log delivery and neighbour state.

## Publication and missing-evidence policy

A completed entry must provide **(1)** the specific authorized lab worksheet or Packet Tracer file and ownership/permission, **(2)** sanitized diagram and device/port roles, **(3)** commands actually issued, **(4)** expected test, **(5)** timestamped actual output or capture, **(6)** analysis of pass/fail plus **real** troubleshooting, and **(7)** verification of benign operation after changes. Maintain separate states for *not attempted*, *attempted but unverified*, and *verified*, without inferring state from a quiz answer. Screenshots must be authorized course-lab captures reviewed for student identities, hostnames, usernames, public/private IPs, keys, shared secrets, tokens and unrelated infrastructure. **Do not use private HomeLab material.** No new screenshots were uploaded in this update.

Source scope: six course slide decks (network threats; network-device security; AAA; ACL/firewalls/ZPF; IDS/IPS; endpoint/LAN), related uploaded notes, quizzes and study discussion. Exam question banks are *not* primary lab evidence, and no question-bank content is reproduced.
